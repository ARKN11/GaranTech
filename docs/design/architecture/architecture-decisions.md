# تصمیم‌های معماری — Architecture Decision Records

## وضعیت و هدف

این سند تصمیم‌های اصلی معماری طراحی اولیه GaranTech و دلیل انتخاب آن‌ها را ثبت می‌کند. هر تصمیم شامل زمینه، انتخاب، گزینه‌های جایگزین و پیامدها است.

وضعیت «پذیرفته‌شده» در این سند به معنی تأیید طراحی اولیه توسط مسئول طراحی در تیم است؛ بازبینی نهایی تیم و استاد درس همچنان می‌تواند باعث اصلاح آن شود.

---

## ADR-001 — استفاده از یک برنامه وب واحد

**وضعیت:** پذیرفته‌شده

### زمینه
مشتری و کارکنان با نقش‌های مختلف از یک سامانه استفاده می‌کنند، اما گردش‌کار و امکانات موردنیاز آن‌ها متفاوت است.

### تصمیم
یک Web Application واحد با بخش‌ها و رابط‌های متناسب با نقش مشتری، کارشناس خدمات، تعمیرکار و مدیر سامانه ایجاد شود.

### گزینه‌های جایگزین
- برنامه وب جداگانه برای مشتری و کارکنان
- برنامه مستقل برای هر نقش

### پیامدها
- کاهش تکرار کد و هزینه نگهداری
- استفاده مجدد از اجزای رابط کاربری
- نیاز به طراحی دقیق مسیریابی و تجربه کاربری نقش‌ها
- کنترل دسترسی باید در بک‌اند نیز انجام شود؛ مخفی‌کردن عناصر رابط کاربری کافی نیست.

---

## ADR-002 — بک‌اند یکپارچه ماژولار (Modular Monolith)

**وضعیت:** پذیرفته‌شده

### زمینه
سامانه چند حوزه مرتبط مانند درخواست تعمیر، بازرسی، گارانتی، پیشنهاد هزینه و تعمیر دارد. نیازمندی فعلی، استقرار مستقل یا مقیاس‌پذیری مستقل این حوزه‌ها را الزام نمی‌کند.

### تصمیم
یک Backend Application واحد ایجاد شود که به ماژول‌های منطقی با مسئولیت مشخص تقسیم شده است.

### گزینه‌های جایگزین
- بک‌اند یکپارچه بدون مرزبندی ماژول‌ها
- معماری Microservices

### پیامدها
- توسعه، اجرا و استقرار ساده‌تر از ریزخدمت‌ها
- امکان حفظ مرزهای مسئولیت در کد
- نیاز به جلوگیری از وابستگی‌های دوری و دسترسی مستقیم نامنظم میان ماژول‌ها
- در صورت تغییر نیازمندی‌ها، امکان بازنگری معماری وجود دارد.

---

## ADR-003 — استفاده از پایگاه داده رابطه‌ای

**وضعیت:** پذیرفته‌شده

### زمینه
مدل داده شامل موجودیت‌های مرتبط، کلیدهای اصلی و خارجی و محدودیت‌های یکپارچگی است.

### تصمیم
اطلاعات پایدار GaranTech در یک پایگاه داده رابطه‌ای نگهداری شود. انتخاب DBMS مشخص به مرحله تصمیم فناوری موکول می‌شود.

### گزینه‌های جایگزین
- پایگاه داده سندگرا
- ذخیره‌سازی غیررابطه‌ای دیگر

### پیامدها
- پشتیبانی مناسب از روابط و قیود یکپارچگی
- پشتیبانی از تراکنش برای عملیات چندمرحله‌ای
- نیاز به طراحی دقیق Schema و Migration در مرحله پیاده‌سازی

---

## ADR-004 — معماری چهارلایه بک‌اند

**وضعیت:** پذیرفته‌شده

### زمینه
ترکیب منطق کسب‌وکار با API و دسترسی پایگاه داده، نگهداری و آزمون‌پذیری سامانه را دشوار می‌کند.

### تصمیم
بک‌اند از چهار لایه تشکیل شود:
1. Presentation
2. Application
3. Domain
4. Infrastructure

### گزینه‌های جایگزین
- قرار دادن منطق در مسیرهای API
- ساختار ساده بدون مرز مشخص میان منطق و زیرساخت

### پیامدها
- جدایی مسئولیت‌ها
- امکان آزمون مستقل‌تر قواعد دامنه
- استقلال بیشتر منطق کسب‌وکار از فریم‌ورک و DBMS
- نیاز به تعریف مرزهای روشن و جلوگیری از ایجاد لایه‌های غیرضروری

---

## ADR-005 — مدیریت متمرکز انتقال وضعیت درخواست

**وضعیت:** پذیرفته‌شده

### زمینه
وضعیت درخواست تحت تأثیر دریافت دستگاه، نتیجه گارانتی، تصمیم مشتری، شروع تعمیر و نتیجه آزمون قرار می‌گیرد. تغییر مستقل وضعیت توسط ماژول‌های مختلف می‌تواند باعث ناسازگاری شود.

### تصمیم
یک مؤلفه مرکزی Status & Tracking مسئول اعتبارسنجی انتقال وضعیت و ثبت تاریخچه باشد. ماژول‌های کسب‌وکار نتیجه عملیات خود را به این مؤلفه اعلام می‌کنند.

### گزینه‌های جایگزین
- تغییر مستقیم وضعیت توسط هر ماژول
- مدیریت وضعیت بدون ثبت تاریخچه متمرکز

### پیامدها
- یکپارچگی بیشتر گردش‌کار
- قابلیت ردیابی تغییرات وضعیت
- نیاز به تعریف دقیق انتقال‌های مجاز و actor هر تغییر
- این مؤلفه نباید جایگزین مسئولیت ماژول‌های کسب‌وکار شود.

### انتقال‌های اصلی مورد انتظار
- REGISTERED → RECEIVED
- RECEIVED → READY_FOR_REPAIR (در صورت واجدشرایط‌بودن گارانتی)
- RECEIVED → INSPECTED (در مسیر خارج از گارانتی)
- INSPECTED → AWAITING_CUSTOMER_DECISION
- AWAITING_CUSTOMER_DECISION → READY_FOR_REPAIR (پذیرش)
- AWAITING_CUSTOMER_DECISION → CANCELLED (رد)
- READY_FOR_REPAIR → IN_REPAIR
- IN_REPAIR → COMPLETED (پس از آزمون نهایی موفق)

لغو در وضعیت‌های مجاز پیش از شروع تعمیر امکان‌پذیر است. پس از شروع تعمیر لغو مجاز نیست. آزمون ناموفق وضعیت را IN_REPAIR نگه می‌دارد.

## ADR-006 — دسترسی امن مشتری به رهگیری بدون حساب کاربری

**وضعیت:** پذیرفته‌شده

### زمینه
مشتری حساب کاربری ندارد و باید بتواند درخواست خود را پیگیری کند. صرف داشتن کد رهگیری نباید دسترسی نامحدود به اطلاعات درخواست ایجاد کند.

### تصمیم
برای دسترسی به اطلاعات رهگیری، کد رهگیری و شماره تلفن ثبت‌شده مشتری با هم بررسی شوند. پاسخ رهگیری به اطلاعات مجاز برای مشتری محدود باشد و تلاش‌های ناموفق مکرر محدودسازی شوند.

### گزینه‌های جایگزین
- دسترسی صرفاً با کد رهگیری
- ایجاد حساب کاربری برای تمام مشتریان

### پیامدها
- حفظ تجربه بدون ثبت‌نام مشتری
- کاهش احتمال افشای اطلاعات با حدس کد رهگیری
- نیاز به نرمال‌سازی شماره تلفن و اعمال محدودیت تلاش
- جزئیات فنی مانند نرخ محدودسازی، انقضای نشست و ثبت رویداد امنیتی در طراحی امنیت و پیاده‌سازی تعیین می‌شود.

---

## ADR-007 — استفاده از تراکنش برای تغییرات مرتبط

**وضعیت:** پذیرفته‌شده

### زمینه
برخی عملیات کسب‌وکار چند رکورد مرتبط را تغییر می‌دهند. برای نمونه پذیرش پیشنهاد هزینه ممکن است تصمیم مشتری، وضعیت درخواست و تاریخچه وضعیت را تغییر دهد.

### تصمیم
تغییرات داده‌ای که باید از نظر کسب‌وکار با هم موفق یا ناموفق باشند، در یک تراکنش پایگاه داده انجام شوند.

### گزینه‌های جایگزین
- ذخیره مستقل هر تغییر بدون تراکنش مشترک
- جبران دستی تغییرات پس از شکست بخشی از عملیات

### پیامدها
- جلوگیری از باقی‌ماندن داده نیمه‌کاره
- سازگاری بهتر وضعیت و تاریخچه
- نیاز به تعریف مرز تراکنش در Application Layer
- عملیات طولانی یا وابسته به سامانه خارجی، در صورت اضافه‌شدن در آینده، نیازمند بازنگری جداگانه است.

---

## ADR-008 — کنترل مجوزها در بک‌اند بر اساس نقش

**وضعیت:** پذیرفته‌شده

### زمینه
نقش‌های Service Expert، Technician و System Admin وظایف و دسترسی‌های متفاوت دارند. رابط کاربری به‌تنهایی مرجع قابل اعتماد برای کنترل مجوز نیست.

### تصمیم
بک‌اند برای هر عملیات محافظت‌شده، هویت کارکنان و مجوز متناسب با نقش را بررسی کند. رابط وب فقط تجربه کاربری متناسب با نقش را نمایش می‌دهد.

### گزینه‌های جایگزین
- اتکا به مخفی‌کردن دکمه‌ها و صفحات در فرانت‌اند
- اعطای دسترسی یکسان به همه کارکنان

### پیامدها
- جلوگیری از اجرای عملیات غیرمجاز از طریق فراخوانی مستقیم API
- نیاز به تعریف ماتریس نقش/مجوز بر اساس Use Caseها
- نیاز به آزمون دسترسی مجاز و غیرمجاز برای عملیات حساس

---

## ADR-009 — استفاده از FastAPI به‌عنوان فریم‌ورک بک‌اند

**وضعیت:** پذیرفته‌شده

### زمینه
GaranTech به یک API برای ارتباط برنامه وب با بک‌اند نیاز دارد. تیم به فریم‌ورکی نیاز دارد که توسعه APIهای HTTP را ساده کند و با ساختار لایه‌ای و ماژولار انتخاب‌شده سازگار باشد.

### تصمیم
**FastAPI** به‌عنوان فریم‌ورک بک‌اند برای ارائه APIهای HTTP/REST انتخاب می‌شود. استفاده از FastAPI در درجه اول به لایه Presentation محدود می‌ماند؛ منطق کاربردی و دامنه نباید به اشیاء Request/Response یا سازوکارهای اختصاصی FastAPI وابسته شوند.

### گزینه‌های جایگزین
- Django و Django REST Framework
- Flask
- پیاده‌سازی با فریم‌ورک‌های دیگر یا بدون فریم‌ورک

### پیامدها
- پشتیبانی مناسب از توسعه API و مستندسازی OpenAPI
- اعتبارسنجی و تعریف قراردادهای ورودی/خروجی در مرز API
- نیاز به رعایت مرز لایه‌ها تا وابستگی FastAPI به Domain نشت نکند
- انتخاب کتابخانه‌های جانبی، احراز هویت، ORM و ابزار Migration همچنان تصمیم‌های جداگانه‌اند.

---

## ADR-010 — استفاده از PostgreSQL به‌عنوان DBMS

**وضعیت:** پذیرفته‌شده

### زمینه
مدل داده GaranTech شامل موجودیت‌های مرتبط، کلیدهای خارجی، محدودیت‌های یکپارچگی و عملیات چندرکوردی است که باید به‌شکل اتمیک ذخیره شوند.

### تصمیم
**PostgreSQL** به‌عنوان سیستم مدیریت پایگاه داده رابطه‌ای پروژه انتخاب می‌شود.

### گزینه‌های جایگزین
- MySQL
- سایر DBMSهای رابطه‌ای
- پایگاه داده غیررابطه‌ای

### پیامدها
- پشتیبانی از روابط، قیود و تراکنش‌های موردنیاز سامانه
- نیاز به طراحی Schema و Migration متناسب با PostgreSQL
- اتصال پایگاه داده فقط از طریق Infrastructure انجام می‌شود
- انتخاب ORM، درایور اتصال و ابزار Migration هنوز در این ADR تعیین نشده است.

---

## بازبینی تصمیم‌ها

این ADRها طراحی اولیه‌اند. پیش از پیاده‌سازی باید:
- با نسخه نهایی SRS و Use Cases تطبیق داده شوند.
- ماتریس دقیق مجوزها مشخص شود.
- جزئیات امنیت رهگیری مشتری تعیین شود.
- فناوری‌های اجرایی بدون تحمیل زودهنگام به معماری انتخاب شوند.
- هر تصمیمی که به‌دلیل نیازمندی جدید تغییر می‌کند، با ثبت وضعیت و دلیل تغییر به‌روزرسانی شود.
