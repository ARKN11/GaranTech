# گزارش بازبینی یکپارچگی مستندات طراحی — GaranTech

**تاریخ بازبینی:** 2026-11-10  
**مبنای نیازمندی:** SRS نسخه 0.3  
**دامنه:** SRS، Use Cases، Activity Diagram، Logical Data Model، ERD، UML Class Diagram، Architecture و UI Prototype  
**وضعیت:** بازبینی اولیه انجام شد؛ تأیید نهایی مشروط به رفع موارد باز و دریافت سناریوی End-to-End عضو چهارم است.

## 1. خلاصه مدیریتی

ساختار اصلی سامانه و مسیر اصلی گردش‌کار در مستندات عمدتاً هماهنگ است:

- مشتری بدون حساب کاربری درخواست را ثبت و با کد رهگیری و شماره تماس ثبت‌شده پیگیری می‌کند.
- دریافت فیزیکی پیش‌نیاز بازرسی است.
- کارشناس وضعیت گارانتی را دستی تعیین می‌کند.
- درخواست واجد شرایط گارانتی مستقیماً به `READY_FOR_REPAIR` می‌رود.
- درخواست خارج از گارانتی به `INSPECTED` و سپس پس از ثبت پیشنهاد به `AWAITING_CUSTOMER_DECISION` می‌رود.
- پذیرش پیشنهاد به `READY_FOR_REPAIR` و رد آن به `CANCELLED` منتهی می‌شود.
- شروع تعمیر فقط از `READY_FOR_REPAIR` انجام می‌شود.
- آزمون ناموفق وضعیت را `IN_REPAIR` نگه می‌دارد و آزمون موفق باعث `COMPLETED` می‌شود.
- مدل منطقی، ERD و Class Diagram هر سه ۱۳ موجودیت اصلی را پوشش می‌دهند و تفکیک تصمیم تعویض دستگاه از عملیات تعویض قطعه را حفظ می‌کنند.
- انتخاب‌های معماری FastAPI، PostgreSQL، Modular Monolith، چهار لایه، مدیریت مرکزی وضعیت و RBAC با یکدیگر سازگارند.

با این حال، چند اختلاف بین نیازمندی و رفتار مستندشده/نمونه اولیه باقی است. موارد زیر باید پیش از تأیید نهایی تعیین تکلیف شوند.

## 2. یافته‌های بازبینی

### CR-01 — نتیجه کارشناسی در نمونه اولیه به‌طور کامل ثبت نمی‌شود
**شدت:** زیاد  
**مراجع:** SRS FR-06 و FR-07، UC-03، Logical Data Model: Inspection و InspectionDefect، UI Prototype

فرم بازرسی در نمونه اولیه فیلد «اقدام پیشنهادی» دارد، اما کنترل آن شناسه مشخصی ندارد و تابع ثبت بازرسی مقدار آن را نمی‌خواند یا ذخیره نمی‌کند. همچنین تابع ثبت بازرسی عیب را فقط اعتبارسنجی می‌کند و آن را در state نمونه اولیه نگه نمی‌دارد. فرم فقط یک عیب را می‌گیرد، در حالی که FR-06 و مدل داده از یک یا چند عیب پشتیبانی می‌کنند.

**اقدام پیشنهادی:**
- برای اقدام پیشنهادی مقدار فنی صریح `REPAIR` یا `DEVICE_REPLACEMENT` تعریف و ذخیره شود.
- عیب‌های ثبت‌شده در state نگهداری و در نمای مجاز مشتری به‌عنوان بخشی از نتیجه کارشناسی نمایش داده شوند.
- امکان افزودن بیش از یک عیب در فرم نمونه اولیه فراهم شود.

### CR-02 — مسیر مغایرت دستگاه در UC-02 در نمونه اولیه اجرا نمی‌شود
**شدت:** زیاد  
**مراجع:** Use Cases UC-02، Logical Data Model: Device، Activity Diagram، UI Prototype

UC-02 می‌گوید اگر دستگاه تحویلی با اطلاعات ثبت‌شده تطبیق نداشت، کارشناس اطلاعات را اصلاح کند و سپس دریافت را ثبت کند. صفحه دریافت یک انتخابگر «تطبیق دارد/مغایرت دارد» نشان می‌دهد، اما این انتخابگر شناسه ندارد و تابع `receiveDevice()` مقدار آن را بررسی نمی‌کند. هیچ فیلد اصلاح مشخصات نیز وجود ندارد. Activity Diagram نیز این جریان جایگزین را نشان نمی‌دهد.

**اقدام پیشنهادی:**
- مشخص شود اصلاح اطلاعات در محدوده این نسخه باقی می‌ماند یا خیر؛ چون در UC-02 فعلی صریحاً آمده، پیشنهاد این است که حفظ شود.
- در صورت حفظ، فیلدهای اصلاح برند/مدل/شماره سریال (متناسب با داده‌های موجود) نمایش داده شوند و ثبت دریافت در حالت مغایرت تا اصلاح اطلاعات مسدود بماند.
- شاخه مغایرت در Activity Diagram اضافه شود.
- اصلاح مشخصات نباید به قابلیت ویرایش عمومی و نامحدود اطلاعات درخواست تبدیل شود.

### CR-03 — مقدار Enum عملیات تعمیر با اعتبارسنجی نمونه اولیه تطبیق ندارد
**شدت:** زیاد  
**مراجع:** Logical Data Model: RepairJobOperation، UML Class Diagram: OperationType، UI Prototype

گزینه‌های نوع عملیات در HTML مقدار `value` صریح ندارند؛ بنابراین مقدار انتخاب‌شده متن کامل گزینه مانند `PART_REPLACEMENT — تعویض قطعه` خواهد بود. در مقابل، تابع ثبت عملیات مقدار را دقیقاً با رشته `PART_REPLACEMENT` مقایسه می‌کند. در نتیجه کنترل اجباری شرح قطعه برای تعویض قطعه قابل اتکا نیست و مقدار ذخیره‌شده نیز با Enum دامنه یکسان نیست.

**اقدام پیشنهادی:**
- برای هر گزینه مقدار فنی صریح `REPAIR`، `PART_REPLACEMENT` و `DEVICE_REPLACEMENT` تعریف شود.
- اعتبارسنجی و مقدار ذخیره‌شده فقط از همین مقادیر فنی استفاده کنند.

### CR-04 — فرم افزودن کارمند با مدل داده و رفتار نمایشی هم‌خوان نیست
**شدت:** زیاد  
**مراجع:** SRS FR-15 و BR-10، Logical Data Model: Staff، UML Class Diagram: Staff، UI Prototype

در مدل داده، `Staff.phone` و `Staff.password_hash` اجباری‌اند؛ اما فرم افزودن کارمند فقط نام، نام کاربری، نقش و فعال/غیرفعال را می‌گیرد. تابع `addStaff()` نیز فقط پیام نمایش می‌دهد و کارمند جدید را در state یا جدول نمایشی اضافه نمی‌کند.

**اقدام پیشنهادی:**
- تیم باید روش ایجاد اعتبارنامه اولیه کارکنان را مشخص کند (رمز اولیه، دعوت/تنظیم رمز یا روش دیگر).
- شماره تماس اجباری در فرم یا در فرایند مشخص ایجاد حساب جمع‌آوری شود.
- نمونه اولیه پس از ثبت معتبر، کارمند را در فهرست نمایشی نشان دهد؛ در عین حال مستندات تصریح کنند که احراز هویت واقعی وجود ندارد.

### CR-05 — ویژگی برند در طراحی آمده اما در SRS تصریح نشده است
**شدت:** متوسط — نیازمند تصمیم تیم  
**مراجع:** SRS FR-02، Logical Data Model: Device، UI Prototype

FR-02 نوع دستگاه، مدل و شماره سریال را نام می‌برد؛ اما مدل داده و نمونه اولیه `brand` را نیز اجباری کرده‌اند.

**اقدام پیشنهادی:** یکی از دو مسیر به‌صورت رسمی انتخاب شود:
1. اگر برند واقعاً داده موردنیاز است، FR-02 و بخش اطلاعات اصلی SRS به‌روزرسانی شوند؛ یا
2. اگر برند نیازمندی نیست، اجباری بودن آن از مدل داده و فرم ثبت درخواست حذف شود.

تا پیش از تصمیم تیم، SRS مرجع اصلی است و نباید اختلاف به‌صورت ضمنی باقی بماند.

### CR-06 — واحد پول در نمونه اولیه با تصمیم ثبت‌شده مدل داده هم‌خوان نیست
**شدت:** متوسط — نیازمند تصمیم تیم  
**مراجع:** Logical Data Model: RepairProposal، UML Class Diagram: RepairProposal، UI Prototype

مدل داده و Class Diagram می‌گویند واحد پول باید در قرارداد پروژه مشخص شود و خودشان واحدی تعیین نمی‌کنند؛ ولی نمونه اولیه مبلغ را صریحاً با «ریال» نمایش می‌دهد.

**اقدام پیشنهادی:** واحد رسمی (مثلاً IRR/ریال) با تأیید تیم تعیین و در مدل داده، Class Diagram، UI و قراردادهای آینده API یکسان ثبت شود. تا آن زمان UI نباید انتخاب تأییدنشده را به‌عنوان تصمیم قطعی نمایش دهد.

### CR-07 — اختیاری بودن یادداشت آزمون در اسناد یکسان نیست
**شدت:** متوسط  
**مراجع:** Logical Data Model: RepairTest، UML Class Diagram: RepairTest، UC-08، UI Prototype

در مدل داده `test_notes` اختیاری است، اما Class Diagram آن را غیرقابل‌تهی نشان می‌دهد و نمونه اولیه برای همه آزمون‌ها یادداشت اجباری می‌خواهد. UC-08 مشخصاً برای آزمون ناموفق ثبت توضیح را لازم می‌داند، اما برای آزمون موفق الزام مشابهی تصریح نشده است.

**اقدام پیشنهادی:** `test_notes` در مدل و UML اختیاری باقی بماند؛ در رابط کاربری توضیح برای `FAILED` اجباری و برای `PASSED` اختیاری باشد، مگر اینکه تیم الزام سخت‌گیرانه‌تری تصویب کند.

### CR-08 — قاعده مبلغ صفر در نمونه اولیه با مدل داده متفاوت است
**شدت:** متوسط  
**مراجع:** Logical Data Model IC-15 و RepairProposal، UML Class Diagram، UI Prototype

مدل داده و Class Diagram مبلغ را نامنفی توصیف می‌کنند؛ بنابراین صفر مجاز است. نمونه اولیه فقط مقادیر بزرگ‌تر از صفر را قبول می‌کند.

**اقدام پیشنهادی:** تیم مشخص کند مبلغ باید «نامنفی» باشد یا «مثبت». سپس IC-15، توضیح متد `validateAmount()` و اعتبارسنجی UI با یک قاعده واحد هماهنگ شوند.

### CR-09 — نمای مشتری با allowlist تعریف‌شده در Class Diagram کاملاً هم‌راستا نیست
**شدت:** متوسط  
**مراجع:** SRS BR-06 و FR-13، UML Class Diagram: CustomerTrackingView، UI Prototype

DTO مشتری وضعیت فعلی، نتیجه گارانتی، اقدام پیشنهادی، عیب‌های تشخیص‌داده‌شده و هزینه پیشنهادی را مجاز می‌داند. نمونه اولیه فعلاً فقط نتیجه گارانتی را نمایش می‌دهد و یک برچسب ثابت نوع/برند دستگاه نیز نشان می‌دهد که در DTO مجاز تعریف نشده است.

**اقدام پیشنهادی:**
- جزئیات نتیجه کارشناسی (عیب‌های تشخیص‌داده‌شده و اقدام پیشنهادی) در نمای مشتری نمایش داده شوند.
- اطلاعات دستگاه از نمای مشتری حذف شود، مگر آنکه تیم رسماً BR-06 را گسترش دهد.
- تاریخچه کامل، یادداشت داخلی، عملیات تعمیر و اطلاعات کارکنان همچنان پنهان بمانند.
- کد رهگیری صرفاً برای شناسایی درخواست نمایش داده شود.

### CR-10 — سناریوی End-to-End و Error Case
**وضعیت:** سند تهیه و در شاخه اصلی ادغام شده؛ بازبینی محتوایی تیم باقی است.  
**مراجع:** تسک طراحی اولیه، `docs/design/end-to-end-scenario.md`

سناریوی کامل درخواست خارج از گارانتی از ثبت تا تکمیل تعمیر، به همراه ردیابی Use Caseها، نیازمندی‌ها، وضعیت‌ها، موجودیت‌ها و لایه‌های معماری تهیه شده است. سناریوی خطای رقابت هم‌زمان بین لغو مشتری و شروع تعمیر نیز رفتار اتمیک مورد انتظار را مشخص می‌کند.

**اقدام باقی‌مانده:** اعضای تیم باید انطباق سناریو با SRS، Use Cases، Activity Diagram، مدل داده، Class Diagram و معماری را بازبینی و تأیید کنند. در صورت یافتن اختلاف، اصلاحات باید در مستندات مرجع ثبت شوند.

## 4. تصمیم‌های لازم از طرف تیم

این موارد را قبل از نهایی‌کردن مستندات به‌صورت تصمیم روشن ثبت کنید:

1. آیا `brand` جزء الزامی اطلاعات دستگاه است؟
2. واحد پول رسمی چیست؟
3. مبلغ پیشنهاد باید مثبت باشد یا نامنفی؟
4. یادداشت آزمون موفق اختیاری است و فقط یادداشت آزمون ناموفق اجباری است؟
5. روش ایجاد اعتبارنامه اولیه کارکنان چیست؟
6. آیا اصلاح مشخصات دستگاه در زمان دریافت، دقیقاً مطابق UC-02 حفظ می‌شود؟

## 5. ترتیب پیشنهادی رفع موارد

1. اصلاح CR-01، CR-02 و CR-03 در UI Prototype و تطبیق Activity Diagram.
2. تعیین CR-04 و CR-05 تا فرم‌ها و مدل داده یک قرارداد واحد داشته باشند.
3. تعیین CR-06، CR-07 و CR-08 و همگام‌سازی مدل داده، Class Diagram و UI.
4. اصلاح نمای مشتری طبق CR-09.
5. بازبینی تیمی سند End-to-End و Error Case طبق CR-10.
6. اجرای بازبینی نهایی و ثبت تأیید طراحی در Change Log.

## 6. نتیجه

**وضعیت فعلی: اصلاحات طراحی و تصمیم‌های تکمیلی اعمال شده‌اند و سند End-to-End User Story و Error Case نیز در main موجود است؛ تأیید نهایی محتوای آن و sign-off تیمی همچنان باقی است.**

یافته‌های بخش 2 وضعیت زمان بازبینی اولیه را ثبت می‌کنند؛ بخش 7 وضعیت جدید و تصمیم‌های اعمال‌شده را به‌عنوان مرجع به‌روز ارائه می‌کند. مدل داده، ERD، Class Diagram، SRS، Use Cases، Activity Diagram و نمونه اولیه اکنون در موارد تصمیم‌گیری‌شده هم‌راستا شده‌اند.

### وضعیت اصلاحات نمونه اولیه
- CR-01: اقدام پیشنهادی و چند عیب در state نمونه اولیه ذخیره می‌شوند و در نمای مشتری به‌عنوان نتیجه کارشناسی مجاز نمایش داده می‌شوند.
- CR-02: شاخه مغایرت و اصلاح مشخصات دستگاه به UI و Activity Diagram اضافه شد.
- CR-03: مقادیر enum عملیات تعمیر به مقادیر فنی صریح متصل شدند.
- CR-04: فرم افزودن کارمند فیلدهای لازم را می‌گیرد و حساب نمایشی را در فهرست ثبت می‌کند؛ رمز خام ذخیره نمی‌شود.
