# مدل داده منطقی (Logical Data Model) — GaranTech

**نام گروه:** توکیو  
**مبنای طراحی:** SRS نسخه 0.3، Use Cases نسخه جاری و Activity Diagram  
**وضعیت:** نسخه بازبینی‌شده برای طراحی اولیه

## 1. هدف و اصول طراحی

این سند ساختار منطقی داده‌های موردنیاز سامانه GaranTech و قواعد ارتباط میان آن‌ها را مشخص می‌کند. مبنا، جریان کاری تعریف‌شده در SRS و Use Cases است؛ بنابراین مدل از افزودن قابلیت‌های خارج از محدوده خودداری می‌کند.

اصول مهم:

- مشتری حساب کاربری ندارد؛ ثبت و پیگیری با شناسه درخواست و شماره تماس ثبت‌شده انجام می‌شود.
- اطلاعات مشتری با شماره تماس نرمال‌شده بازیابی می‌شود؛ در صورت وجود، رکورد قبلی استفاده می‌شود.
- وضعیت گارانتی را کارشناس خدمات به‌صورت دستی تعیین می‌کند.
- درخواست تحت گارانتی مستقیماً به وضعیت «آماده تعمیر» می‌رود و به پیشنهاد هزینه یا تصمیم مشتری نیاز ندارد.
- برای درخواست خارج از گارانتی، یک پیشنهاد هزینه ثبت می‌شود و مشتری آن را می‌پذیرد یا رد می‌کند.
- تصمیم کارشناسی درباره «تعمیر یا تعویض دستگاه» با عملیات واقعی تعمیرکار و «تعویض قطعه» متفاوت است.
- آزمایش ناموفق، درخواست را در وضعیت «در حال تعمیر» نگه می‌دارد و آزمایش می‌تواند تکرار شود.
- وضعیت‌های «تکمیل‌شده» و «لغوشده» را سامانه تعیین می‌کند.

### علائم و قراردادها

- **PK:** کلید اصلی
- **FK:** کلید خارجی
- **UQ:** مقدار یکتا
- **NOT NULL:** اجباری
- **NULL:** اختیاری
- **1:N:** یک به چند
- **1:0..1:** یک به صفر یا یک

شناسه‌ها در این مدل به‌صورت منطقی تعریف شده‌اند؛ نوع فیزیکی آن‌ها (مانند UUID یا BIGINT) در مرحله مدل فیزیکی تعیین می‌شود.

## 2. موجودیت‌ها و ویژگی‌ها

### 2.1 Customer — مشتری

اطلاعات تماس مشتری را نگهداری می‌کند. مشتری در سامانه حساب کاربری یا رمز عبور ندارد.

| ویژگی | قید | توضیح |
|---|---|---|
| customer_id | PK | شناسه مشتری |
| full_name | NOT NULL | نام و نام خانوادگی |
| phone_number | NOT NULL, UQ | شماره تماس نرمال‌شده |
| created_at | NOT NULL | زمان ایجاد رکورد |

**قاعده:** هنگام ثبت درخواست، سامانه ابتدا شماره تماس نرمال‌شده را جست‌وجو می‌کند. اگر مشتری وجود داشت، همان رکورد استفاده می‌شود؛ در غیر این صورت رکورد جدید ایجاد می‌شود. نرمال‌سازی شماره تماس باید پیش از بررسی یکتایی انجام شود.

### 2.2 Device — دستگاه

مشخصات دستگاهی را نگهداری می‌کند که برای آن درخواست ثبت شده است.

| ویژگی | قید | توضیح |
|---|---|---|
| device_id | PK | شناسه دستگاه |
| category | NOT NULL | نوع دستگاه: MOBILE یا LAPTOP |
| brand | NULL | سازنده (اختیاری؛ تکمیل‌کننده FR-02) |
| model | NOT NULL | مدل |
| serial_number | NULL | شماره سریال، در صورت وجود |
| created_at | NOT NULL | زمان ایجاد رکورد |

یک دستگاه می‌تواند در طول زمان در چند درخواست تعمیر ثبت شود. این رابطه به معنی وجود سامانه انبار یا مدیریت مالکیت دستگاه نیست.

### 2.3 RepairRequest — درخواست تعمیر

هسته اصلی سامانه و نماینده چرخه عمر هر درخواست است.

| ویژگی | قید | توضیح |
|---|---|---|
| request_id | PK | شناسه داخلی درخواست |
| tracking_code | NOT NULL, UQ | شناسه قابل استفاده برای پیگیری |
| customer_id | FK, NOT NULL | ارجاع به Customer |
| device_id | FK, NOT NULL | ارجاع به Device |
| initial_description | NOT NULL | شرح اولیه مشکل از طرف مشتری |
| current_status | NOT NULL | وضعیت فعلی درخواست |
| submitted_at | NOT NULL | زمان ثبت |
| updated_at | NOT NULL | آخرین زمان به‌روزرسانی |
| cancelled_at | NULL | زمان لغو |
| cancellation_reason | NULL | دلیل لغو، در صورت ثبت |

**قواعد:**
- هر درخواست دقیقاً متعلق به یک مشتری و یک دستگاه است.
- مشتری با ترکیب tracking_code و شماره تماس ثبت‌شده درخواست را پیگیری می‌کند.
- لغو فقط پیش از شروع تعمیر مجاز است.
- اگر درخواست لغو شود، cancelled_at باید مقدار داشته باشد.
- تغییر current_status باید مطابق انتقال‌های مجاز UC-12 باشد و در StatusHistory ثبت شود.

### 2.4 Staff — کارکنان سامانه

اطلاعات حساب و نقش کارکنان را نگهداری می‌کند. این موجودیت برای کارشناس خدمات، تعمیرکار و مدیر سامانه استفاده می‌شود.

| ویژگی | قید | توضیح |
|---|---|---|
| staff_id | PK | شناسه کارمند |
| full_name | NOT NULL | نام و نام خانوادگی |
| phone | NOT NULL | شماره تماس |
| email | NULL, UQ | ایمیل، در صورت ثبت |
| username | NOT NULL, UQ | نام کاربری ورود |
| password_hash | NOT NULL | هش رمز عبور؛ هرگز متن خام رمز ذخیره نمی‌شود |
| role | NOT NULL | SERVICE_EXPERT، TECHNICIAN یا ADMIN |
| is_active | NOT NULL | فعال یا غیرفعال بودن حساب |
| created_at | NOT NULL | زمان ایجاد حساب |

**قواعد:** فقط کارکنان حساب ورود دارند. نقش هر حساب در نسخه فعلی یکی از سه نقش تعریف‌شده است. مدیریت حساب و نقش‌ها بر عهده مدیر سامانه است. عملیات هر نقش باید در لایه برنامه با نقش مناسب محدود شود.

### 2.5 DeviceReceipt — دریافت حضوری دستگاه

تحویل فیزیکی دستگاه به فروشگاه را ثبت می‌کند.

| ویژگی | قید | توضیح |
|---|---|---|
| receipt_id | PK | شناسه رسید |
| request_id | FK, NOT NULL, UQ | درخواست مربوط؛ حداکثر یک رسید برای هر درخواست |
| received_by_staff_id | FK, NOT NULL | کارشناس خدمات دریافت‌کننده |
| received_at | NOT NULL | زمان دریافت |
| notes | NULL | توضیحات تکمیلی |

**قاعده:** ثبت دریافت حضوری توسط کارشناس خدمات انجام می‌شود. پیش از ثبت دریافت، کارشناسی دستگاه مجاز نیست.

### 2.6 Inspection — نتیجه کارشناسی

نتیجه بررسی فیزیکی، وضعیت گارانتی و تصمیم پیشنهادی کارشناس را ثبت می‌کند.

| ویژگی | قید | توضیح |
|---|---|---|
| inspection_id | PK | شناسه کارشناسی |
| request_id | FK, NOT NULL, UQ | درخواست مربوط؛ یک کارشناسی در نسخه فعلی |
| service_expert_id | FK, NOT NULL | کارشناس خدمات |
| warranty_result | NOT NULL | ELIGIBLE یا NOT_ELIGIBLE |
| warranty_rejection_reason | NULL | دلیل خارج بودن از گارانتی |
| recommended_action | NOT NULL | REPAIR یا DEVICE_REPLACEMENT |
| inspection_notes | NULL | توضیحات کارشناسی |
| inspected_at | NOT NULL | زمان ثبت نتیجه کارشناسی |

**قواعد:**
- فقط کارشناس خدمات می‌تواند نتیجه کارشناسی را ثبت کند.
- ثبت نتیجه کارشناسی پس از DeviceReceipt انجام می‌شود.
- اگر warranty_result برابر NOT_ELIGIBLE باشد، دلیل رد گارانتی الزامی است.
- recommended_action تصمیم کارشناس درباره تعمیر یا تعویض کل دستگاه است؛ با تعویض قطعه توسط تعمیرکار یکسان نیست.
- یک درخواست در نسخه فعلی حداکثر یک رکورد کارشناسی دارد؛ پشتیبانی از کارشناسی مجدد در نیازمندی فعلی تعریف نشده است.

### 2.7 InspectionDefect — ایراد تشخیص‌داده‌شده

یک یا چند ایرادی را نگهداری می‌کند که کارشناس هنگام بررسی دستگاه تشخیص می‌دهد. شرح اولیه مشتری جداگانه در RepairRequest نگهداری می‌شود.

| ویژگی | قید | توضیح |
|---|---|---|
| defect_id | PK | شناسه ایراد |
| inspection_id | FK, NOT NULL | کارشناسی مربوط |
| title | NOT NULL | عنوان ایراد |
| description | NOT NULL | شرح ایراد |

هر کارشناسی باید حداقل یک ایراد تشخیص‌داده‌شده داشته باشد.

### 2.8 RepairProposal — پیشنهاد هزینه تعمیر

مبلغ پیشنهادی تعمیر خارج از گارانتی را نگهداری می‌کند.

| ویژگی | قید | توضیح |
|---|---|---|
| proposal_id | PK | شناسه پیشنهاد |
| inspection_id | FK, NOT NULL, UQ | کارشناسی مربوط؛ حداکثر یک پیشنهاد |
| estimated_total_cost | NOT NULL | مبلغ کل پیشنهادی |
| notes | NULL | توضیحات پیشنهاد |
| created_at | NOT NULL | زمان ایجاد پیشنهاد |

**قواعد:**
- این موجودیت فقط برای نتیجه کارشناسی NOT_ELIGIBLE ایجاد می‌شود.
- برای درخواست تحت گارانتی پیشنهاد هزینه و تصمیم مشتری ایجاد نمی‌شود؛ درخواست مستقیماً آماده تعمیر است.
- مبلغ پیشنهادی، مبلغ کل اعلام‌شده به مشتری است. در نیازمندی فعلی الزام مشخصی برای ریزکردن مبلغ به ازای هر عملیات وجود ندارد؛ بنابراین موجودیت ProposalItem اضافه نشده است.
- مبلغ پیشنهادی باید بزرگ‌تر از صفر باشد (IC-15).
- واحد پول رسمی پروژه IRR (ریال ایران) است؛ همه مبالغ در مدل داده، API و رابط کاربری با همین واحد تفسیر می‌شوند.

### 2.9 CustomerDecision — تصمیم مشتری

پاسخ مشتری به پیشنهاد هزینه خارج از گارانتی را ثبت می‌کند.

| ویژگی | قید | توضیح |
|---|---|---|
| decision_id | PK | شناسه تصمیم |
| proposal_id | FK, NOT NULL, UQ | پیشنهاد مربوط؛ حداکثر یک تصمیم نهایی |
| decision | NOT NULL | ACCEPTED یا REJECTED |
| decided_at | NOT NULL | زمان تصمیم |
| customer_note | NULL | توضیح مشتری |

**قواعد:**
- این موجودیت فقط برای پیشنهاد هزینه خارج از گارانتی استفاده می‌شود.
- پذیرش پیشنهاد، درخواست را به READY_FOR_REPAIR می‌برد.
- رد پیشنهاد، درخواست را به CANCELLED می‌برد.
- تصمیم نهایی هر پیشنهاد فقط یک بار ثبت می‌شود.

### 2.10 RepairJob — فرایند تعمیر

شروع و مسئولیت فرایند تعمیر یا تعویض دستگاه را ثبت می‌کند.

| ویژگی | قید | توضیح |
|---|---|---|
| repair_job_id | PK | شناسه فرایند تعمیر |
| request_id | FK, NOT NULL, UQ | درخواست مربوط؛ حداکثر یک فرایند |
| technician_id | FK, NOT NULL | تعمیرکار مسئول |
| started_at | NOT NULL | زمان شروع تعمیر |
| completed_at | NULL | زمان تکمیل موفق |

**قواعد:**
- فرایند تعمیر فقط پس از READY_FOR_REPAIR آغاز می‌شود.
- شروع تعمیر وضعیت درخواست را IN_REPAIR می‌کند و پس از آن لغو توسط مشتری مجاز نیست.
- یک RepairJob می‌تواند چند عملیات و چند آزمایش نهایی داشته باشد.
- تکمیل فرایند پس از ثبت آزمایش موفق انجام می‌شود.

### 2.11 RepairJobOperation — عملیات انجام‌شده

عملیات واقعی تعمیرکار را ثبت می‌کند. این موجودیت مستقل از پیشنهاد هزینه است تا هم تعمیرات تحت گارانتی و هم تعمیرات خارج از گارانتی را پوشش دهد.

| ویژگی | قید | توضیح |
|---|---|---|
| job_operation_id | PK | شناسه عملیات |
| repair_job_id | FK, NOT NULL | فرایند تعمیر مربوط |
| operation_type | NOT NULL | REPAIR، PART_REPLACEMENT یا DEVICE_REPLACEMENT |
| description | NOT NULL | شرح عملیات انجام‌شده |
| part_description | NULL | شرح قطعه تعویض‌شده، در صورت وجود |
| operation_status | NOT NULL | PENDING، IN_PROGRESS یا COMPLETED |
| completed_at | NULL | زمان پایان عملیات |

**قواعد:**
- هر فرایند تعمیر شامل یک یا چند ردیف عملیات است.
- اطلاعات قطعه صرفاً به‌صورت توضیح ثبت می‌شود؛ مدیریت انبار یا کاتالوگ قطعات خارج از محدوده است.
- DEVICE_REPLACEMENT به تعویض کل دستگاه اشاره دارد و با PART_REPLACEMENT متفاوت است.

### 2.12 RepairTest — آزمایش نهایی

نتیجه هر نوبت آزمایش نهایی را نگهداری می‌کند.

| ویژگی | قید | توضیح |
|---|---|---|
| repair_test_id | PK | شناسه آزمایش |
| repair_job_id | FK, NOT NULL | فرایند تعمیر مربوط |
| tested_by_staff_id | FK, NOT NULL | تعمیرکار ثبت‌کننده نتیجه |
| result | NOT NULL | PASSED یا FAILED |
| test_notes | NULL | توضیحات آزمایش |
| tested_at | NOT NULL | زمان آزمایش |

**قواعد:**
- نتیجه آزمایش را تعمیرکار ثبت می‌کند.
- در صورت FAILED، درخواست در IN_REPAIR باقی می‌ماند و عملیات و آزمایش می‌تواند تکرار شود.
- در صورت PASSED، سامانه درخواست را COMPLETED می‌کند.
- همه نتایج آزمایش قبلی نگهداری می‌شوند.

### 2.13 StatusHistory — تاریخچه وضعیت

تمام تغییرات وضعیت درخواست را ثبت می‌کند.

| ویژگی | قید | توضیح |
|---|---|---|
| history_id | PK | شناسه رکورد تاریخچه |
| request_id | FK, NOT NULL | درخواست مربوط |
| actor_type | NOT NULL | CUSTOMER، STAFF یا SYSTEM |
| changed_by_staff_id | FK, NULL | کارمند آغازکننده تغییر، در صورت وجود |
| previous_status | NULL | وضعیت قبلی؛ برای رکورد اولیه NULL |
| new_status | NOT NULL | وضعیت جدید |
| changed_at | NOT NULL | زمان تغییر |
| note | NULL | توضیح تغییر |

**قواعد:**
- با ایجاد درخواست، یک رکورد اولیه با previous_status برابر NULL و new_status برابر REGISTERED ایجاد می‌شود.
- اگر actor_type برابر STAFF باشد، changed_by_staff_id الزامی است.
- اگر actor_type برابر CUSTOMER یا SYSTEM باشد، changed_by_staff_id باید NULL باشد؛ مشتری از طریق RepairRequest قابل شناسایی است.
- وضعیت‌های نهایی COMPLETED و CANCELLED را سامانه تعیین می‌کند.
- این تاریخچه برای ممیزی داخلی است؛ مشتری طبق BR-06 فقط وضعیت فعلی، نتیجه کارشناسی و هزینه پیشنهادی را می‌بیند.

## 3. مقادیر مجاز (Enums)

### 3.1 وضعیت درخواست — RepairRequest.current_status و StatusHistory

| مقدار فنی | عنوان فارسی |
|---|---|
| REGISTERED | ثبت‌شده |
| RECEIVED | دریافت‌شده |
| INSPECTED | بررسی‌شده |
| AWAITING_CUSTOMER_DECISION | در انتظار تصمیم مشتری |
| READY_FOR_REPAIR | آماده تعمیر |
| IN_REPAIR | در حال تعمیر |
| COMPLETED | تکمیل‌شده |
| CANCELLED | لغوشده |

این فهرست دقیقاً با SRS نسخه 0.3 و UC-12 هماهنگ است. مقدار APPROVED در مدل قبلی حذف شده و با READY_FOR_REPAIR جایگزین شده است.

### 3.2 سایر مقادیر

| ویژگی | مقادیر |
|---|---|
| Device.category | MOBILE, LAPTOP |
| Staff.role | SERVICE_EXPERT, TECHNICIAN, ADMIN |
| Inspection.warranty_result | ELIGIBLE, NOT_ELIGIBLE |
| Inspection.recommended_action | REPAIR, DEVICE_REPLACEMENT |
| CustomerDecision.decision | ACCEPTED, REJECTED |
| RepairJobOperation.operation_type | REPAIR, PART_REPLACEMENT, DEVICE_REPLACEMENT |
| RepairJobOperation.operation_status | PENDING, IN_PROGRESS, COMPLETED |
| RepairTest.result | PASSED, FAILED |
| StatusHistory.actor_type | CUSTOMER, STAFF, SYSTEM |

| RepairRequest | دارای تاریخچه است | StatusHistory | 1:N |
| Staff | ممکن است آغازکننده تغییر باشد | StatusHistory | 1:0..N |

در روابط اختیاری، رکورد سمت وابسته ممکن است تا پیش از رسیدن فرایند به آن مرحله وجود نداشته باشد.

## 5. قواعد یکپارچگی و اعتبارسنجی

| شناسه | قاعده |
|---|---|
| IC-01 | شماره تماس نرمال‌شده مشتری یکتا است. |
| IC-02 | tracking_code یکتا است. |
| IC-03 | هر درخواست دقیقاً به یک مشتری و یک دستگاه ارجاع می‌دهد. |
| IC-04 | هر درخواست حداکثر یک DeviceReceipt دارد. |

## 6. جریان وضعیت درخواست

انتقال‌های مجاز طبق UC-12:

| وضعیت قبلی | وضعیت جدید | محرک |
|---|---|---|
| REGISTERED | RECEIVED | ثبت دریافت حضوری، UC-02 |
| RECEIVED | READY_FOR_REPAIR | کارشناسی تحت گارانتی، UC-03 |
| RECEIVED | INSPECTED | کارشناسی خارج از گارانتی، UC-03 |
| INSPECTED | AWAITING_CUSTOMER_DECISION | اعلام هزینه، UC-04 |
| AWAITING_CUSTOMER_DECISION | READY_FOR_REPAIR | پذیرش هزینه، UC-05 |
| AWAITING_CUSTOMER_DECISION | CANCELLED | رد هزینه، UC-05 |
| REGISTERED، RECEIVED، INSPECTED، AWAITING_CUSTOMER_DECISION، READY_FOR_REPAIR | CANCELLED | لغو مشتری، UC-06 |
| READY_FOR_REPAIR | IN_REPAIR | شروع تعمیر، UC-07 |
| IN_REPAIR | COMPLETED | آزمایش موفق، UC-08 |

در آزمایش ناموفق هیچ انتقال وضعیتی رخ نمی‌دهد و درخواست در IN_REPAIR باقی می‌ماند.

## 7. موارد خارج از مدل

برای جلوگیری از توسعه بی‌مورد مدل، موارد زیر در این نسخه موجودیت مستقلی ندارند:

- حساب کاربری مشتری و احراز هویت مشتری
- انبار، موجودی و کاتالوگ قطعات
- پرداخت و حسابداری
- اتصال به سامانه‌های بیرونی گارانتی
- چند پیشنهاد جایگزین برای یک کارشناسی
- پیشنهاد هزینه برای تعمیر تحت گارانتی
- گزارش‌های آماری مدیریتی
- تاریخچه قابل مشاهده برای مشتری

## 8. نکات بازبینی و فرض‌های صریح

1. یک درخواست در نسخه فعلی حداکثر یک کارشناسی دارد؛ اگر Use Case جدیدی برای کارشناسی مجدد اضافه شود، قید یکتایی request_id در Inspection باید بازبینی شود.
2. هر کارشناسی حداکثر یک پیشنهاد هزینه دارد؛ پیشنهاد فقط برای حالت خارج از گارانتی استفاده می‌شود.
3. مبلغ پیشنهادی در سطح RepairProposal ذخیره می‌شود؛ ریزهزینه هر عملیات در نیازمندی فعلی تعریف نشده است.
4. عملیات واقعی مستقل از پیشنهاد هزینه ثبت می‌شوند تا تعمیر تحت گارانتی نیز پشتیبانی شود.
5. شماره سریال اختیاری است؛ شناسه داخلی دستگاه مبنای رابطه است.
6. این مدل منطقی است و هنوز درباره نوع فیزیکی ستون‌ها، ایندکس‌های بهینه‌سازی، موتور پایگاه داده یا ORM تصمیم نمی‌گیرد.
