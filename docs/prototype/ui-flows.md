# جریان‌های کاربری و وضعیت‌های رابط کاربری GaranTech

**نسخه:** 1.0  
**مبنای طراحی:** SRS نسخه 0.3، Use Cases، Activity Diagram، مدل داده منطقی و معماری مصوب

این سند جریان‌های اصلی نمونه اولیه و وضعیت‌های قابل مشاهده رابط کاربری را مشخص می‌کند. نمونه اولیه صرفاً نمایشی است و داده‌ها در حافظه مرورگر نگهداری می‌شوند.

## 1. ساختار ناوبری

### بخش مشتری
- ثبت درخواست جدید
- پیگیری درخواست
- جزئیات درخواست
- تصمیم درباره پیشنهاد هزینه
- لغو درخواست

### بخش کارکنان
- ورود کارکنان
- میز کارشناس خدمات
- ثبت دریافت فیزیکی دستگاه
- ثبت نتیجه بازرسی و گارانتی
- ثبت پیشنهاد هزینه
- میز کار تعمیرکار
- ثبت عملیات تعمیر
- ثبت نتیجه آزمون

### بخش مدیریت
- داشبورد مدیر سامانه
- مدیریت کارکنان

## 2. جریان‌های اصلی

### 2.1 ثبت درخواست مشتری
1. مشتری نام، شماره تلفن، نوع دستگاه، برند، مدل و شرح اولیه مشکل را وارد می‌کند.
2. شماره تماس و فیلدهای اجباری اعتبارسنجی می‌شوند.
3. درخواست با وضعیت `REGISTERED` ایجاد می‌شود و کد رهگیری به مشتری نمایش داده می‌شود.
4. مشتری برای پیگیری باید کد رهگیری و همان شماره تلفن ثبت‌شده را ارائه کند.

### 2.2 دریافت فیزیکی و بازرسی
1. کارشناس خدمات درخواست ثبت‌شده را پیدا می‌کند.
2. دریافت حضوری دستگاه را ثبت می‌کند؛ وضعیت به `RECEIVED` تغییر می‌کند.
3. فرم بازرسی تا قبل از ثبت دریافت غیرفعال است.
4. کارشناس باید حداقل یک عیب با عنوان و شرح ثبت کند و وضعیت گارانتی و اقدام پیشنهادی را تعیین کند.
5. در حالت `NOT_ELIGIBLE` ثبت دلیل رد گارانتی اجباری است.
6. اگر گارانتی واجد شرایط باشد، درخواست مستقیماً `READY_FOR_REPAIR` می‌شود؛ در غیر این صورت `INSPECTED` می‌شود.

### 2.3 پیشنهاد هزینه و تصمیم مشتری
1. پیشنهاد هزینه فقط پس از تکمیل بازرسی و فقط برای نتیجه `NOT_ELIGIBLE` قابل ثبت است.
2. مبلغ کل پیشنهادی باید عددی و بزرگ‌تر از صفر باشد.
3. پس از ثبت پیشنهاد، وضعیت به `AWAITING_CUSTOMER_DECISION` تغییر می‌کند.
4. مشتری با کد رهگیری و شماره تماس ثبت‌شده پیشنهاد را می‌بیند و می‌پذیرد یا رد می‌کند.
5. پذیرش، وضعیت را به `READY_FOR_REPAIR` می‌برد؛ رد پیشنهاد درخواست را `CANCELLED` می‌کند.

### 2.4 تعمیر و آزمون
1. تعمیرکار فقط از وضعیت `READY_FOR_REPAIR` می‌تواند تعمیر را شروع کند.
2. با شروع تعمیر، وضعیت `IN_REPAIR` می‌شود و لغو مشتری دیگر مجاز نیست.
3. تعمیرکار یک یا چند عملیات ثبت می‌کند؛ برای تعویض قطعه، شرح قطعه نیز لازم است.
4. ثبت آزمون به وجود حداقل یک عملیات تعمیر وابسته است.
5. آزمون ناموفق، درخواست را در `IN_REPAIR` نگه می‌دارد و امکان ثبت عملیات و آزمون مجدد وجود دارد.
6. آزمون موفق، وضعیت را به `COMPLETED` تغییر می‌دهد.

## 3. وضعیت‌های رابط کاربری

| وضعیت UI | نمونه رفتار |
|---|---|
| Initial / Empty | فهرست خالی یا نبود عملیات ثبت‌شده با پیام راهنما نمایش داده می‌شود. |
| Loading | در نمونه مستقل و بدون API، بارگذاری شبکه وجود ندارد؛ در نسخه متصل به API باید هنگام ارسال/دریافت درخواست نمایش داده شود. |
| Validation error | فیلد اجباری خالی، شماره تلفن نامعتبر، مبلغ نامعتبر یا نبود عیب/شرح عملیات با پیام خطا رد می‌شود. |
| Workflow blocked | کنترل بازرسی پیش از دریافت دستگاه و ثبت پیشنهاد پیش از بازرسی خارج از گارانتی غیرفعال است؛ توابع نیز شرط را دوباره بررسی می‌کنند. |
| Not found / Failure | کد رهگیری یا شماره تماس نامنطبق پیام «درخواست یافت نشد» می‌دهد. |
| Success | پس از ثبت درخواست، دریافت، بازرسی، پیشنهاد، تصمیم مشتری، عملیات یا آزمون پیام تأیید نمایش داده می‌شود. |
| Confirmation | لغو درخواست با پیام هشدار و امکان انصراف نمایش داده می‌شود. |
| Disabled | عملیات نامعتبر با توجه به وضعیت گردش‌کار غیرفعال می‌شود. |

## 4. اطلاعات قابل مشاهده برای مشتری

مطابق BR-06 مشتری فقط وضعیت فعلی درخواست، نتیجه کارشناسی و هزینه پیشنهادی را مشاهده می‌کند. تاریخچه کامل وضعیت‌ها، یادداشت‌های داخلی، جزئیات عملیات تعمیر و اطلاعات کارکنان در نمای مشتری نمایش داده نمی‌شوند.

## 5. محدودیت نمونه اولیه

- داده‌ها نمایشی و در حافظه صفحه هستند و با بارگذاری مجدد مرورگر از بین می‌روند.
- احراز هویت و مجوزدهی واقعی وجود ندارد؛ انتخاب نقش صرفاً برای نمایش مسیرهای مختلف است.
- هیچ API، پایگاه داده، ارسال پیامک/ایمیل، پرداخت یا اتصال بیرونی وجود ندارد.
- اعتبارسنجی‌های رابط کاربری جایگزین اعتبارسنجی و کنترل دسترسی سمت سرور در محصول واقعی نیستند.
